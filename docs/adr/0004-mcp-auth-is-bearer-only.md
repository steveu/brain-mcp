# MCP auth is bearer-only; no Cloudflare Access on /mcp

Public ingress to brain-mcp sits behind Cloudflare Tunnel on `brain.urmston.org`, and the only auth tier on `/mcp` is the existing DCR bearer-token OAuth flow (`/register`, `/authorize`, `/token`, `WWW-Authenticate` discovery on 401). Cloudflare Access in front of `/mcp` was considered as a "defence in depth" second tier and rejected.

The claude.ai connector — the entire reason this server is public — calls `/mcp` from its backend, not from a browser. It sends `Authorization: Bearer <token>` after completing the DCR + `/authorize` flow during setup. There is no `CF_Authorization` cookie on those requests, because there is no browser session: claude.ai's tool-call traffic is server-to-server. So any cookie-based Cloudflare Access policy on `/mcp` either intercepts every tool call and returns its HTML login page (breaking the connector), or bypasses `/mcp` entirely (in which case Access protects nothing — the bypass-everything-except-`/.well-known/*`-and-`/{register,authorize,token}` shape that surface-level guides recommend turns out to cover exactly the OAuth setup surface, while leaving the actual data path either broken or unprotected). Cloudflare Access service tokens (`CF-Access-Client-Id` / `CF-Access-Client-Secret` headers) could in principle satisfy a non-cookie policy, but claude.ai's custom-connector UI doesn't accept arbitrary headers — only the OAuth fields — so service tokens are unreachable from the actual client. The bearer-token tier is therefore the only tier the connector can satisfy, and adding Access on top of it can only break or no-op.

Revisit if either of two things changes: (a) claude.ai's connector grows support for arbitrary headers, making Cloudflare Access service tokens a real option for `/mcp`; or (b) a non-MCP, browser-fronted endpoint is added to this service (e.g. an admin UI) that would actually benefit from cookie-based SSO. In the second case, Access belongs in front of that endpoint, not `/mcp`.
