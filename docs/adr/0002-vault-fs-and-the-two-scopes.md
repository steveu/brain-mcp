# Vault filesystem primitives live in one module; the two scopes don't

ADR-0001 established that writes are vault-scoped and reads are allowlist-scoped — two distinct trust boundaries. As a follow-on, we consolidated the path-resolution, symlink-safe walking, and `read(path)` primitives into a single module (`src/vault-fs.ts`) that sits beneath both `vault-read.ts` and `vault-write.ts`. The module exposes **two distinct resolve entry points** — `resolveUnderVault` (write side) and `resolveInAllowlist` (read side) — sharing internal primitives but never collapsing into one fused operation. The collapse was tempting on duplication grounds and was the framing in the originating issue, but it would either widen the read surface (forcing write roots into the allowlist) or invent a parallel write-allowlist; ADR-0001 rules both out.

The walk rule is unified across all callers: follow symlinks only when the canonical target stays inside the same allowlisted entry. This flattens a previous inconsistency where `redact.ts` skipped symlinks entirely while `vault-read.ts`'s walks followed them within-entry. One quiet consequence: dotfiles (`.foo`) are now uniformly skipped, including by the redact basename index — a wikilink like `[[.private]]` will redact where it might previously have resolved. Accepted as a tightening, not a regression.

`allowlist.ts` is intentionally kept as a thin data layer (`loadAllowlist`, `Allowlist`/`AllowlistEntry` types). Per-call operations live in `vault-fs.ts`. Redaction stays in `redact.ts`: `vault-fs.read(path)` returns raw text, and the read-tool layer is responsible for redacting before returning to the agent. The trust boundary `vault-fs` enforces is "did this path escape its scope" — not "do the wikilinks inside this file point out of scope". Keeping those concerns separate keeps the module's surface focused.
